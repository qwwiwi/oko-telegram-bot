# Архитектура Oko Telegram Bot («Око»)

Документ описывает, как устроен бот, на основе кода в `archive/` и миграций в `migrations/`. Пользовательская часть – в [README.md](../README.md), база данных – в [database.md](database.md), эксплуатация – в [operations.md](operations.md).

## Что делает система и чего не делает

Бот читает обновления своего Telegram-бота через облачный Bot API (`https://api.telegram.org`, методы `getUpdates` и `getFile`) и складывает их в PostgreSQL и на диск. Это архив «вперёд»: сообщения, которые Telegram не доставил боту, в архив не попадут.

- Нет истории до добавления бота и до подтверждения владельца.
- Нет обнаружения удалений в обычных группах: Telegram не присылает ботам такие обновления.
- Telegram хранит неполученные обновления ограниченное время; если поллер долго не работал, часть обновлений теряется.
- Сообщения других ботов Telegram боту не доставляет.
- Файлы больше 20 МиБ не скачиваются (лимит облачного Bot API), остаются метаданные со статусом `oversized_not_downloaded`.
- Альбом хранится как отдельные сообщения с общим `media_group_id`.
- Локальный сервер Bot API не используется.

## Компоненты

Один образ приложения, разные команды (`python -m archive --config settings.toml <команда>`):

| Компонент | Команда | Роль |
|---|---|---|
| `db` | – | PostgreSQL 16; порт наружу не публикуется |
| `poller` | `poller` | Единственный читатель Telegram: `getUpdates`, запись обновлений в базу, курсор |
| `worker` | `worker` | Очередь задач: скачивание файлов, расшифровка, сообщения владельцу, выход из неизвестных чатов |
| `api` | `api` | Только чтение: HTTP API на `127.0.0.1:8610` |
| `ops` | `migrate`, `status`, `export`, `transcripts requeue`, `audit prune` | Разовые команды оператора |

Стек: Python 3.12+, FastAPI, psycopg 3, httpx. SQL пишется напрямую, ORM нет. Poller и worker ходят наружу только на `api.telegram.org` (и к провайдерам расшифровки, если они включены). Контейнеры приложения запускаются без привилегий, с файловой системой только для чтения.

## Приём обновлений

1. При старте поллер проверяет личность бота (`getMe` должен вернуть `expected_bot_id`) и отсутствие вебхука (`getWebhookInfo`). Вебхук поллер сам не удаляет и `logOut` не вызывает; при конфликте двух читателей (ответ 409) он останавливается.
2. Поллер берёт сеансовую блокировку PostgreSQL (`pg_try_advisory_lock`) на своём соединении. Потеря соединения означает потерю владения; второй поллер на той же базе не запустится.
3. Каждый новый владелец повышает «эпоху» курсора и продолжает с сохранённого смещения (`poll_state.next_offset`). Курсор двигается в той же транзакции, что и запись обновления, поэтому сбой до коммита приводит к повторной обработке, а после коммита повтор безвреден.
4. Дубли исключены хэшем: уникальный `events.fingerprint` – SHA-256 канонического JSON обновления.
5. Запрашиваются только `message`, `edited_message`, `channel_post`, `edited_channel_post`, `my_chat_member`, `callback_query`.
6. Если после 6 дней без коммитов Telegram мог сменить нумерацию, поллер читает с `offset=0` до следующего коммита.

Что происходит с обновлением – по статусу чата в `chat_approvals`:

- чат `active` и не выключен в настройках – обновление сохраняется;
- чат ждёт решения, отклонён, остановлен или удалён – обновление подтверждается и отбрасывается, растёт только счётчик `dropped`;
- чат без записи (бот попал в группу без обновления о добавлении) – содержимое не сохраняется, ставится задача `leaveChat` и числовой ID попадает в часовую сводку владельцу; личные чужие чаты не покидаются, их ID хранится 24 часа;
- личные сообщения владельца боту – разбирается только команда `/chats`, ничего не сохраняется.

Для сохраняемого сообщения в одной транзакции пишутся `events` (сырой JSON), `revisions` (версия), `messages` (текущая версия, обновляется только более новой правкой), `attachments` и задачи на скачивание. Порядок правок определяется временем правки (`edit_date`, иначе `date`), затем порядком событий. Правка, пришедшая раньше оригинала, создаёт сообщение; опоздавшая старая версия не затирает новую.

Обновления, которые не удалось разобрать, не блокируют очередь: после трёх попыток (счётчик `mapping_failures`) или сразу при детерминированной ошибке данных они сохраняются в `events` с `error_code` (карантин), курсор двигается, получателю оповещений (`founder_id`) уходит сообщение с кодом и ID чата. Временные сбои базы курсор не двигают.

## Подтверждение чатов

Состояния `chat_approvals.status`: `pending`, `active`, `declined`, `stopped`, `removed`, `expired`. Переходы: «Да» (из `pending`, `declined`, `stopped`) – `active`; «Нет» (из `pending`) – `declined`; «Стоп» (из `active`) – `stopped`. Повторные и устаревшие нажатия безопасны. Нажатия принимаются только от `owner_tg_id` в его личном чате с ботом; формат данных кнопок строго ограничен.

Результат работы воркера (файл, расшифровка) публикуется в транзакции, которая держит строку одобрения (`FOR SHARE`): если чат остановлен в момент работы, файл удаляется, а вложение получает статус `blocked`. При переходе группы в супергруппу решение владельца переносится на новый ID, старая запись помечается `migrated_to`; доступ агентов при этом не расширяется автоматически.

## Файлы

Воркер скачивает файл потоком по адресу `https://api.telegram.org/file/bot<токен>/<путь>`: без редиректов, без сжатия, с таймаутами и общим сроком, с ограничением по размеру (по `Content-Length` и по фактическим байтам), со SHA-256. Данные пишутся во временный файл с правами 0600 и публикуются атомарно, только если размер, контрольная сумма и аренда задачи совпали. Путь строится из идентификаторов (`<slug>/<chat_id>/<дата>/<id вложения>/<идентификатор аренды>/file`), имя файла от отправителя не используется. Токен не попадает в журналы, ошибки и базу. Файл, чей размер выше лимита, получает статус `oversized_not_downloaded` и никогда не повторяется.

## Очередь задач

Таблица `jobs`: статусы `pending`, `running`, `done`, `failed`; аренда с токеном и сроком; выбор через `FOR UPDATE SKIP LOCKED`; отдельное соединение продлевает аренду во время долгих операций; число попыток и экспоненциальная пауза ограничены. Приоритет: владельческие сообщения и выход из чатов, затем скачивание, затем расшифровка. Устаревший владелец аренды не может записать результат.

## Расшифровка

Включается тремя условиями (глобально, по чату, ключ). Groq принимает файлы до 20 000 000 байт, AssemblyAI – крупнее; резервного перехода между ними нет. Перед отправкой в AssemblyAI идентификатор заявки сохраняется в базе, опрос идёт отдельными задачами, повторной отправки при неопределённом исходе нет – статус `reconciliation_required` требует решения оператора. Срок опроса ограничен 24 часами с момента создания задачи. Подробно – README, «Расшифровка голосовых и видео».

## HTTP API и ключи

Только чтение. Ключ на агента: в `settings.toml` хранится SHA-256 ключа и явный список чатов; сравнение выполняется за постоянное время. Чат виден агенту, если он в его списке, хотя бы раз одобрен владельцем и не отключён флагом `enabled = false`. Архив ранее одобренного чата остаётся читаемым после «Стоп». Файлы выдаются только ключам с `files = true`, всегда как `application/octet-stream` с `Content-Disposition: attachment`. Лимит запросов – скользящее окно в памяти одного процесса API. Каждый запрос к `/v1/...` пишет строку в `read_audit`. Автодокументация (OpenAPI) отключена; все ответы с `Cache-Control: no-store`.

Содержимое чатов для агента – непроверенные данные, а не инструкции. Сводка дня (`summary`) – детерминированная выгрузка: вопросы и решения в ней не классифицируются.

## Экспорт

`export --chat ID --date ГГГГ-ММ-ДД` пишет `<export_root>/<slug>/chat/ГГГГ-ММ-ДД.json` и `.md` атомарной заменой. День считается по Europe/Moscow (константа в коде). Каталог должен быть абсолютным, с правами 700 и вне любого дерева git.

## Устройство базы

Миграции `migrations/001`…`005` применяет команда `migrate`: по порядку, один раз, под блокировкой, номера пишутся в `schema_version`. Таблицы, связи и индексы описаны в [database.md](database.md). Сырой JSON обновлений хранится в `bytea` (а не `jsonb`), чтобы ограничения PostgreSQL на символы не мешали сохранить доказательство; производные текстовые поля нормализуют символ NUL.

## Тесты и проверки

`scripts/check.sh` создаёт одноразовый PostgreSQL 16 в приватном временном каталоге (только unix-сокет), затем: проверка состава файлов и поиска токенов в исходниках, статическая проверка Compose, `ruff`, тесты, сквозной тест API. Тесты идут на настоящем PostgreSQL; Telegram и провайдеры расшифровки имитируются HTTP-транспортом, поэтому они не доказывают работу с живыми сервисами.
