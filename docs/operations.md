# Эксплуатация Oko Telegram Bot («Око»)

Повседневные задачи оператора. Установка – в [README.md](../README.md), база и резервные копии – в [database.md](database.md). Команды даны для Docker Compose в каталоге репозитория; `ops` – сервис для разовых команд.

## Файлы и права

| Что | Требование |
|---|---|
| `.env` | секреты (токен, пароль базы, ключи расшифровки), `chmod 600`, не в git |
| `settings.toml` | без секретов, обычный файл (не ссылка), `chmod 600`, владелец `10001:10001` для контейнеров |
| `$OKO_DATA_DIR/db` | владелец `999:999`, `700` |
| `$OKO_DATA_DIR/media`, `$OKO_DATA_DIR/exports` | владелец `10001:10001`, `700`; каталоги не вложены друг в друга |

Не выводите `docker compose config` с раскрытыми значениями: используйте `docker compose config --quiet`.

## Добавить, остановить, изменить чат

- **Добавить.** Убедитесь, что `poller` работает, добавьте бота в чат, нажмите «Да» в личном сообщении от бота. Режим приватности должен быть выключен или бот должен быть администратором (каналам нужен администратор). После смены режима приватности удалите бота из чата и добавьте снова.
- **Список и состояние.** `/chats` в личных сообщениях с ботом. Метки: «собираю», «ждёт решения», «на паузе», «бот удалён», «нет ответа», «выключен в конфиге».
- **Остановить.** Карточка чата → «Стоп» → «Да, остановить». Уже собранное остаётся. «Включить» возобновляет.
- **Срочно отключить без бота.** Остановите `api`, затем `worker` и `poller`; поставьте `enabled = false` для чата в `settings.toml`; поднимите сервисы. Настройки читаются при старте.
- **Агентам.** Добавьте ID чата в `chats` ключа в `settings.toml` и пересоздайте `api`: `docker compose up -d --force-recreate api`. Чат виден, только если владелец его одобрил. Автоматически список агентов не расширяется, в том числе при переходе группы в супергруппу: добавьте новый ID вручную.
- **Удалить данные чата.** [database.md](database.md), раздел 7.

## Состояние и мониторинг

```sh
docker compose run --rm ops status
```

Печатает JSON: `poller` (`last_poll`, `last_commit`, `failures`), число задач по статусам, число файлов по статусам, число чатов по статусам, возраст самой старой ожидающей задачи. В выводе нет токенов, путей, ID чатов и текстов.

На что смотреть:

- `last_poll` не обновляется – поллер не работает (`docker compose ps`, `docker compose logs poller`);
- растёт `failures` – временные сбои; при достижении `alert_threshold` (по умолчанию 5) получатель оповещений получает сообщение;
- много задач `failed` – смотрите `SELECT kind, error_code, count(*) FROM jobs WHERE status='failed' GROUP BY 1, 2`;
- файлы в `failed` или `oversized_not_downloaded` – `SELECT status, error_code, count(*) FROM attachments GROUP BY 1, 2`.

Оповещения (в сообщения получателю `founder_id`) приходят о: превышении порога сбоев поллера, карантине обновления, неудачном выходе из неизвестной группы, проверке охвата, переносе группы в супергруппу. Они приходят изнутри процессов бота: если упал весь процесс, оповещения не будет. Настройте внешний мониторинг (проверка `docker compose ps`, свежесть `last_poll`) и срабатывание задолго до срока хранения необработанных обновлений в Telegram.

`GET /health` отвечает `{"status":"ok"}` без ключа и подходит для проверки доступности.

## Ключи API агентов

Создание: README и [database.md](database.md), 6.1. Смена ключа: создайте новый ключ, замените `sha256` в `settings.toml`, пересоздайте `api`, проверьте, что старый ключ получает 401, а новый – 200. Чтение `read_audit`:

```sql
SELECT at, agent, route, chat_id, status, result_count FROM read_audit
WHERE at > now() - interval '1 day' ORDER BY at DESC LIMIT 100;
SELECT agent, status, count(*) FROM read_audit
WHERE at > now() - interval '7 days' GROUP BY 1, 2 ORDER BY 1, 2;
```

Очистка: `docker compose run --rm ops audit prune --days 180` (печатает `pruned N`). Автоматического запуска нет.

## Расшифровка: повторная постановка

Если расшифровка была выключена или не хватало ключа, а потом вы всё настроили, заблокированные ранее расшифровки можно поставить в очередь:

```sh
docker compose run --rm ops transcripts requeue --dry-run     # только показать
docker compose run --rm ops transcripts requeue               # выполнить
docker compose run --rm ops transcripts requeue --chat -1001234567890
```

Вывод: `requeued N, skipped_submitted M, skipped_mismatch K`. Повторно ставятся только записи со статусом `blocked` и кодом `consent_required` или `key_required` в чатах, где сбор включён, оба согласия включены, файл скачан и читается. Уже отправленные провайдеру записи пропускаются (`skipped_submitted`). Статусы `unsupported_format`, `chat_disabled`, `ready`, `reconciliation_required` не восстанавливаются: при неопределённом исходе отправки автоматической повторной отправки (и повторного платежа провайдеру) нет.

## Смена токенов и ключей

- **Токен бота.** Выпустите новый в BotFather, остановите `poller` и `worker`, поменяйте `ARCHIVE_BOT_TOKEN` в `.env` (число до двоеточия должно совпадать с `expected_bot_id`; другой бот потребует нового `expected_bot_id` и отдельной базы), пересоздайте сервисы: `docker compose up -d --force-recreate api poller worker`. На один токен должен быть ровно один читатель `getUpdates`.
- **Пароль базы.** Смените пароль роли в PostgreSQL (`ALTER ROLE archive PASSWORD '…'`), обновите `POSTGRES_PASSWORD` и `ARCHIVE_DATABASE_DSN` в `.env`, пересоздайте сервисы.
- **Ключи Groq и AssemblyAI.** Замените значения в `.env`, пересоздайте `worker`. Если ключ утёк, отзовите его у провайдера.

## Типичные сбои

| Симптом | Причина и действие |
|---|---|
| Поллер перезапускается, в журнале `archive_command_failed` | Не прошла проверка настроек или личности бота, либо у токена есть вебхук (`webhook_present`), либо второй процесс читает те же обновления (409). Проверьте токен, `expected_bot_id`, что другой экземпляр остановлен; вебхук бот не удаляет сам. |
| `private_config_permissions_required` и подобные | Права `settings.toml` шире `600` или это ссылка. |
| Бот не видит сообщения группы | Включён режим приватности и бот не администратор. |
| Нет запроса «Собирать сообщения?» | Вы не нажимали Start у бота в личных сообщениях, не совпал `owner_tg_id`, поллер остановлен. |
| Файл `oversized_not_downloaded` | Больше 20 МиБ; скачать нельзя (лимит облачного Bot API). |
| `/v1/files` отвечает 403 | У ключа `files = false`. |
| API отвечает 429 | Превышен `rate_per_minute`; подождите `Retry-After`. |

## Обновление

```sh
git pull
docker compose build
docker compose run --rm ops migrate     # безопасно повторять: применяет только новые миграции
docker compose up -d
```

Перед обновлением снимите резервную копию ([database.md](database.md), 7.4). Откат кода допустим только к версии, совместимой с уже применённой схемой; данные и каталог `media` не удаляйте. Не используйте `docker compose down -v` и не сбрасывайте курсор вручную.

## Восстановление после сбоя

Восстановление из копии – [database.md](database.md), 7.4. Курсор чтения лежит в базе (`poll_state`), поэтому после восстановления поллер продолжает с сохранённого смещения и подбирает обновления, которые Telegram ещё не удалил; остальные потеряны. Дубли исключены хэшем обновления.

Обновления, помещённые в карантин (`events.error_code` не пусто), остаются в базе с сырым JSON; автоматического повтора нет, их разбор – ручная работа оператора.
