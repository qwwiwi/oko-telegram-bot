# Oko Telegram Bot («Око»)

«Око» – бот-архив для Telegram-чатов. Вы добавляете бота в группу, супергруппу или канал, подтверждаете сбор в личных сообщениях, и бот записывает все новые сообщения чата: текст, правки, ответы, вложения и расшифровки голосовых. Данные лежат в вашей базе PostgreSQL и на диске вашего сервера. Забрать их можно командой экспорта, через HTTP API с ключом или обычным SQL.

Для кого: для администраторов чатов и сообществ, которым нужен собственный архив переписки для поиска, аналитики и работы AI-агентов. Каждый участник сообщества разворачивает своего бота на своём сервере и экспортирует только свои чаты.

## Как это работает

```
Telegram ──getUpdates──▶ poller ──▶ PostgreSQL (events, messages, revisions, attachments, …)
                                        ▲   │
              Telegram ◀──getFile── worker ─┴──▶ файлы на диске (media)
                                        │
                                        └──▶ расшифровка (Groq / AssemblyAI, если включена)

PostgreSQL + media ──▶ api (HTTP, 127.0.0.1:8610)  ──▶ ваши агенты и скрипты (ключ API)
                  └──▶ CLI export (JSON и Markdown за день)
                  └──▶ SQL (psql, роль только для чтения)
```

Четыре процесса из одного образа: `poller` читает обновления Telegram (long polling), `worker` скачивает файлы и вызывает расшифровку, `api` отдаёт данные по HTTP, `db` – PostgreSQL. Разовые команды (`migrate`, `export`, `status`) запускает сервис `ops`. Подробно – в [docs/architecture.md](docs/architecture.md).

## Какие данные собираются

Бот собирает данные только из чатов, которые владелец одобрил кнопкой «Да». Таблица ниже составлена по коду и миграциям `migrations/*.sql`.

| Что | Какие поля | Где хранится |
|---|---|---|
| Сообщение (текущая версия) | ID чата, ID сообщения, время отправки, числовой ID автора (пусто у постов канала), текст или подпись к медиа, ID сообщения, на которое ответили, ID альбома | таблица `messages` |
| История правок | на каждую правку: текст, время правки | таблица `revisions` |
| Сырое обновление Telegram | полный JSON обновления в том виде, как его прислал Telegram: имя и @username автора, название чата, пересылки, форматирование, темы форумов, опросы, геопозиции, контакты и всё прочее, что пришло вместе с сообщением; хэш для защиты от дублей | таблица `events` (столбец `raw`) |
| Служебные события чата (вступление и выход участников, закрепление, смена названия) | сохраняются как сообщения с пустым текстом; подробности – в сыром JSON | `messages`, `events` |
| Вложения: фото, документ, голосовое, аудио, видео, видеосообщение, анимация, стикер, превью | тип, ID файла в Telegram, заявленный размер, MIME, статус, размер, SHA-256, относительный путь | метаданные – `attachments`; сам файл – на диске в `media` |
| Расшифровки голосовых, аудио и видео | текст, провайдер, статус | таблица `transcripts` |
| Членство самого бота в чате | запись о добавлении, удалении, изменении прав бота | `events` |
| Название чата и решение владельца | название (до 128 символов), статус, кто и когда решил, счётчик отброшенных обновлений | таблица `chat_approvals` |
| Журнал чтений через API | время, имя ключа, шаблон пути, ID чата, HTTP-код, число записей | таблица `read_audit` |
| Служебные данные | курсор чтения Telegram, очередь задач, числовые ID неизвестных чатов на 24 часа | `poll_state`, `jobs`, `unknown_chats` и др. |

Что бот **не** собирает:

- сообщения, отправленные до добавления бота и до ответа «Да»: истории нет, сбор идёт с момента подтверждения. Пока чат ждёт решения, отклонён или остановлен, обновления отбрасываются, ведётся только счётчик `dropped`;
- чаты, в которых бота нет; секретные чаты;
- личные переписки с ботом. Исключение – команды владельца в его личных сообщениях с ботом (`/chats` и кнопки): они обрабатываются, но не сохраняются. Для чужого личного чата хранится только числовой ID на 24 часа в служебных таблицах;
- удаление сообщений: Telegram не присылает ботам уведомлений об удалении в обычных группах, поэтому удалённое в Telegram остаётся в архиве;
- сообщения других ботов: Telegram их боту не доставляет;
- реакции, голоса в опросах и прочие обновления: бот запрашивает у Telegram только `message`, `edited_message`, `channel_post`, `edited_channel_post`, `my_chat_member` и `callback_query`;
- файлы больше 20 МиБ (20 971 520 байт): это лимит облачного Bot API. Для такого вложения остаются метаданные и статус `oversized_not_downloaded`, байтов и расшифровки нет;
- сообщения, которых Telegram боту не доставил: в группе бот видит обычные сообщения, только если он администратор или у него выключен режим приватности (см. ниже).

Бот не пишет в чаты и не отвечает участникам. Он отправляет сообщения только владельцу в личку: запрос на подтверждение, список чатов и служебные оповещения с числовыми ID чатов.

## Что пишется в журналы

Журналы процессов (`docker compose logs`):

- в процессах бота логируются только фиксированные коды и счётчики, например `poll_retry`, `read_audit_failed`, `callback_refused`, `quarantine_raw_omitted`. В коде всего несколько вызовов логирования, и ни один не принимает текст сообщения, имя, токен или адрес запроса;
- по умолчанию выводятся предупреждения и ошибки; информационные сообщения вида `chat_approval_requested` не выводятся, пока вы сами не настроите логирование;
- адреса запросов к Telegram содержат токен бота, поэтому журнал запросов `httpx`, `httpcore` и журнал доступа `uvicorn` отключены; текст исключений заменяется фиксированными кодами;
- если команда падает, она печатает только `archive_command_failed` без трассировки. Это сделано, чтобы в журнал не попали токены и пути. Для диагностики смотрите `ops status`, столбцы `error_code` в таблицах `jobs`, `attachments`, `transcripts`, `events` и состояние контейнеров.

Журнал чтений API (таблица `read_audit`): каждый запрос к маршрутам `/v1/...` пишет одну строку – время, имя ключа, шаблон пути (например `/v1/chats/{chat_id}/messages`), ID чата, HTTP-код и число записей в ответе. Строки с неизвестным или отсутствующим ключом пишутся с пустым именем, не более 60 в минуту на процесс. Запросы с верным ключом, на которые API ответил 429 (превышен лимит), оставляют не больше одной строки на ключ за минуту. Если строку журнала записать не удалось, запрос агента возвращает ошибку 500 вместо данных. Очистка: `docker compose run --rm ops audit prune --days 180`.

Что не пишется ни в журналы процессов, ни в `read_audit`: токен бота, ключи API и расшифровки, ключи агентов, строки запросов, тела запросов, тексты сообщений. Сами сообщения хранятся только в базе и на диске (таблица выше).

## Подтверждение чата: как чат попадает в архив

1. Вы добавляете бота в группу, супергруппу или канал. Бот записывает чат со статусом `pending` и пишет владельцу (`owner_tg_id`) в личку: «Меня добавили в чат «Название». Собирать сообщения?» с кнопками «Да» и «Нет». До ответа ничего из чата не сохраняется. Решать может только пользователь с `owner_tg_id`: нажатия других людей отклоняются.
2. «Да» – чат становится `active`, сбор идёт с этого момента. «Нет» – `declined`.
3. Нет ответа 7 дней – статус `expired`, бот выходит из чата; при повторном добавлении он спросит снова. Одновременно ожидать решения могут не больше 100 чатов; сверх лимита чат считается неизвестным.
4. `/chats` в личных сообщениях с ботом – список чатов (по 40 на странице). Нажатие на чат открывает карточку: состояние, имена авторов (не владелец, не `staff`, не боты), число сообщений, вложений, время последнего сообщения, ссылка «Открыть чат» для супергрупп.
5. **Как остановить сбор:** в карточке «Стоп» и подтверждение «Да, остановить». Новые сообщения перестают сохраняться, уже скачанные данные остаются и читаются через API. «Включить» возобновляет сбор. Если убрать бота из чата, статус станет `removed`. Аварийный выключатель оператора: `enabled = false` для чата в `settings.toml` отключает сбор и чтение по API независимо от решения в боте.
6. **Как удалить данные чата:** остановите сбор, затем выполните SQL-удаление и очистку файлов – пошагово в [docs/database.md](docs/database.md), раздел 7. Автоматического удаления в боте нет.

Запускайте бота до того, как добавляете его в чат. Если обновление о добавлении бота потерялось (например, поллер не работал дольше, чем Telegram хранит неполученные обновления), а потом пришли сообщения из этого чата, бот считает чат неизвестным и выходит из него.

## Быстрый старт

Требования:

- сервер Linux с Docker и Docker Compose v2 (`docker compose`), исходящий HTTPS на `api.telegram.org`;
- PostgreSQL 16 (в комплекте как контейнер, отдельно ставить не нужно). Другие версии не проверялись;
- диск под базу, файлы и копии: оценка и формулы – в [docs/database.md](docs/database.md), раздел 3. Фиксированной цифры нет, она зависит от вашего чата;
- Python и `uv` нужны только для разработки и тестов.

1. **Создайте бота в BotFather.** `/newbot`, сохраните токен. Затем выключите режим приватности: `/mybots` → ваш бот → Bot Settings → Group Privacy → Turn off. Без этого, пока бот не администратор, Telegram не доставит ему обычные сообщения группы. Каналам всегда нужен администратор. После смены режима приватности удалите бота из чата и добавьте снова. Откройте бота в личных сообщениях и нажмите Start: иначе он не сможет написать вам запрос на подтверждение.
2. **Узнайте свой числовой Telegram ID** – это `owner_tg_id`.
3. **Склонируйте репозиторий и подготовьте файлы:**

   ```sh
   git clone https://github.com/qwwiwi/oko-telegram-bot.git
   cd oko-telegram-bot
   cp .env.example .env && chmod 600 .env
   cp settings.example.toml settings.toml
   ```

   В `.env` впишите токен бота (`ARCHIVE_BOT_TOKEN`) и пароль базы (`openssl rand -hex 24`; одно и то же значение в `POSTGRES_PASSWORD` и в `ARCHIVE_DATABASE_DSN`). В `settings.toml` впишите `expected_bot_id` (число до двоеточия в токене) и `owner_tg_id`.
4. **Каталоги данных и права:**

   ```sh
   sudo mkdir -p /var/lib/oko/db /var/lib/oko/media /var/lib/oko/exports
   sudo chown 999:999 /var/lib/oko/db
   sudo chown 10001:10001 /var/lib/oko/media /var/lib/oko/exports
   sudo chmod 700 /var/lib/oko/db /var/lib/oko/media /var/lib/oko/exports
   sudo chown 10001:10001 settings.toml && sudo chmod 600 settings.toml
   ```

   Приложение отказывается читать `settings.toml`, если файл доступен группе или всем.
5. **Соберите образ, запустите базу, примените миграции, запустите бота:**

   ```sh
   docker compose build
   docker compose up -d db
   docker compose run --rm ops migrate        # печатает: migration_ok
   docker compose up -d
   ```

6. **Проверка:**

   ```sh
   docker compose ps
   curl -s http://127.0.0.1:8610/health        # {"status":"ok"}
   docker compose run --rm ops status          # JSON: состояние поллера, очередь, число чатов по статусам
   ```

7. **Добавьте бота в чат и подтвердите.** Бот пришлёт вам запрос, нажмите «Да». Отправьте в чат сообщение и убедитесь, что оно в базе:

   ```sh
   docker compose exec db psql -U archive -d archive -c 'SELECT chat_id, title, status FROM chat_approvals'
   docker compose exec db psql -U archive -d archive -c 'SELECT message_id, sent_at, left(text, 40) FROM messages ORDER BY sent_at DESC LIMIT 5'
   ```

Если вы выбрали внешнюю базу (Supabase или свой PostgreSQL, [docs/database.md](docs/database.md), раздел 9): каталог `db` и `POSTGRES_PASSWORD` не нужны, а все команды `docker compose up` и `docker compose run` запускайте с `--no-deps` (шаг 5: `docker compose build`, затем `docker compose run --rm --no-deps ops migrate`, затем `docker compose up -d --no-deps api poller worker`; шаг 6: `docker compose run --rm --no-deps ops status`). Права на `settings.toml` и каталоги `media` и `exports` (шаг 4) нужны в любом варианте.

Образы `postgres` и базовые образы закреплены по хэшам в `compose.yaml` и `Dockerfile`. Сборка образа и запуск контейнеров в этой подготовке не выполнялись: проверялись код, тесты и SQL на PostgreSQL 16 без Docker.

## Как организовать базу

Выбор базы – отдельное решение: маленький проект (один владелец, несколько чатов) запускается на одном экономном контейнере PostgreSQL, большой – на своём Supabase или внешнем PostgreSQL. Код работает только с PostgreSQL. Схема таблиц, готовые SQL-запросы для владельца и AI-агента, роль только для чтения, удаление данных, резервные копии и перенос с малого варианта на большой – в [docs/database.md](docs/database.md).

## Выгрузка данных

Все способы получить данные из архива. Числовой ID чата берётся из `chat_approvals` (запрос выше).

**1. CLI-экспорт за один день (JSON и Markdown).**

```sh
docker compose run --rm ops export --chat -1001234567890 --date 2025-10-09
```

Результат: `$OKO_DATA_DIR/exports/<slug чата>/chat/2025-10-09.json` и `.md`. `slug` – `chat<ID>` или значение из `settings.toml`. Границы дня считаются по часовому поясу Europe/Moscow (пояс зашит в коде). В JSON – сообщения дня с ID автора и временем, все правки с сырым JSON, метаданные вложений, расшифровки; Markdown короче: номер сообщения, текст, состояние файлов и расшифровок. Байты файлов в экспорт не входят. Чат должен быть хотя бы раз одобрен владельцем. Экспорт нужно запускать по дню; для диапазона выполните команду в цикле.

**2. HTTP API с ключом.** Сначала создайте ключ для агента (раздел [«Для AI-агента»](#для-ai-агента) и [docs/database.md](docs/database.md), 6.1), затем:

```sh
KEY=...   # ваш ключ; в settings.toml лежит только его SHA-256
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:8610/v1/chats
curl -s -H "Authorization: Bearer $KEY" "http://127.0.0.1:8610/v1/chats/-1001234567890/messages?from=2025-10-09T00:00:00Z&to=2025-10-10T00:00:00Z&limit=50"
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:8610/v1/chats/-1001234567890/messages/5
curl -s -H "Authorization: Bearer $KEY" "http://127.0.0.1:8610/v1/search?q=счёт&limit=20"
curl -s -H "Authorization: Bearer $KEY" -o file.bin http://127.0.0.1:8610/v1/files/1
curl -s -H "Authorization: Bearer $KEY" "http://127.0.0.1:8610/v1/chats/-1001234567890/summary?date=2025-10-09"
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:8610/v1/status
```

- Ответы – JSON. Сообщения: `{"items": [...], "next_cursor": <число или null>}`; следующую страницу берите параметром `cursor=<next_cursor>`. `limit` от 1 до 100, по умолчанию 50. Параметры `from` и `to` – время в UTC (`Z` или `+00:00`), иначе ошибка 422 `utc_required`. Есть фильтр `author=<ID автора>`. Поиск – буквальная подстрока в тексте и расшифровках, параметры `q`, `chat_id`, `limit`, `cursor`.
- Деталь сообщения (`/messages/ID`) содержит все правки с сырым JSON, вложения и состояние расшифровок. `/summary` – детерминированная выгрузка дня (Europe/Moscow), вопросы и решения в ней помечены как неклассифицированные.
- `/v1/files/ID` отдаёт файл как `application/octet-stream`, если у ключа `files = true`; иначе 403. Вложение без скачанного файла отвечает 409 с причиной, неизвестное или чужое – 404.
- Ключ передаётся только заголовком `Authorization: Bearer`. Нет ключа или он неверный – 401, превышен лимит – 429 с `Retry-After`. Интерактивной документации API нет.
- API слушает только `127.0.0.1:8610`. Для удалённого доступа поставьте перед ним reverse proxy с TLS или используйте SSH-туннель; не открывайте порт в интернет напрямую.

**3. SQL.** Готовые запросы и выгрузка в CSV через `psql \copy` – [docs/database.md](docs/database.md), раздел 5. Для агентов и аналитики создайте роль только для чтения (раздел 6).

**4. Резервная копия** (`pg_dump`) тоже содержит все данные – раздел 7.4 в [docs/database.md](docs/database.md).

## Расшифровка голосовых и видео

Поддерживаются два внешних провайдера (запросы уходят по HTTPS, в провайдер отправляется сам файл):

| Провайдер | Когда используется | Ключ |
|---|---|---|
| Groq (модель `whisper-large-v3`) | файлы до 20 000 000 байт | `GROQ_API_KEY` |
| AssemblyAI | файлы больше 20 000 000 байт | `ASSEMBLYAI_API_KEY` |

Расшифровываются голосовые, аудио, видео и видеосообщения, уже скачанные на диск. Резервного провайдера нет: при ошибке запрос не переадресуется другому. Для неизвестных аудиоформатов расшифровка блокируется со статусом `unsupported_format`.

Расшифровка выключена по умолчанию и требует трёх условий одновременно: `transcription_enabled = true` в `settings.toml`, `transcription = true` для конкретного чата в `[chats."ID"]` и ключ нужного провайдера в `.env`. Чтобы **выключить**, оставьте `transcription_enabled = false` (значение по умолчанию): файлы в чатах продолжат скачиваться, расшифровки получат статус `blocked`, ничего не уйдёт во внешние сервисы. После включения заблокированные ранее расшифровки можно поставить в очередь: `docker compose run --rm ops transcripts requeue --dry-run` (затем без `--dry-run`; можно добавить `--chat ID`).

## Настройка

Секреты и параметры контейнеров – переменные окружения (`.env`); остальное – `settings.toml` (файл без секретов).

### Переменные окружения

Приложение читает четыре переменные (`archive/config.py`); остальные нужны Docker Compose.

| Переменная | Обязательна | По умолчанию | Значение |
|---|---|---|---|
| `ARCHIVE_BOT_TOKEN` | да | – | Токен бота из BotFather. Число до двоеточия должно совпасть с `expected_bot_id`. |
| `ARCHIVE_DATABASE_DSN` | да | – | Строка подключения к PostgreSQL (URI или строка libpq). |
| `GROQ_API_KEY` | нет | пусто | Ключ Groq для расшифровки файлов до 20 000 000 байт. |
| `ASSEMBLYAI_API_KEY` | нет | пусто | Ключ AssemblyAI для файлов крупнее. |

## Резервная копия, восстановление, обновление, удаление

**Резервная копия и восстановление.** База: `docker compose exec -T db pg_dump -U archive -Fc archive > oko.dump`; файлы: `sudo tar -C /var/lib/oko -cf oko-media.tar media`. Восстановление и проверка, что копия восстанавливается, – [docs/database.md](docs/database.md), раздел 7.4 и [docs/operations.md](docs/operations.md).

**Обновление:**

```sh
git pull
docker compose build
docker compose run --rm ops migrate
docker compose up -d
```

**Удаление бота и данных.** `docker compose down`; уберите бота из чатов и отзовите токен в BotFather; удалите каталог `/var/lib/oko` и копии (это необратимо). Не используйте `docker compose down -v` и не удаляйте каталог данных, пока не убедились, что копия есть.

## Правила и ответственность

- Предупредите участников чата, что чат архивируется: кто и где хранит данные, кто имеет к ним доступ, как попросить удалить свои сообщения.
- Получите согласие участников там, где этого требует закон вашей страны и правила площадки. Бот не проверяет согласие и не заменяет его. Отдельно учтите, что расшифровка отправляет файлы внешнему провайдеру (Groq или AssemblyAI), а облачная база (например, Supabase) выносит данные за пределы вашего сервера.
- Данные остаются на сервере владельца бота. Автор репозитория их не получает и не имеет к ним доступа; бот отправляет данные только в Telegram, а при включённой расшифровке – выбранному вами провайдеру.
- Не добавляйте бота в чаты, которыми вы не управляете и в которых у вас нет права собирать данные.
- Автор и участники проекта не отвечают за то, как вы используете бота и что собираете. Программа распространяется «как есть», без гарантий (см. лицензию).
- Это не юридическая консультация; требования к персональным данным в вашей стране проверьте самостоятельно.

## Разработка и проверки

Проверки локальные, GitHub Actions в репозитории нет:

```sh
git config core.hooksPath .githooks     # включает pre-push
TMPDIR=/путь/к/приватному/каталогу sh scripts/check.sh
```

`scripts/check.sh` поднимает одноразовый кластер PostgreSQL 16 (нужны `initdb`, `pg_ctl`, `postgres`, `createdb`; при необходимости задайте `POSTGRES_BIN`), затем запускает проверку состава файлов (`scripts/design_check.py`), проверку Compose (`scripts/compose_check.py`), `ruff`, весь набор тестов и сквозной тест API на localhost. Тесты используют синтетические данные: Telegram и провайдеры расшифровки в них имитируются.
